# I18N.md — translation system & migration ledger

Status: **P1 foundation delivered + one complete slice** (global chrome, home page, article-detail chrome).
Source of truth for copy: `zh-CN`. Second audience: `en` (humans + agent/machine callers).

---

## 1. Public API

```
src/lib/i18n/
  config.ts          locale registry, cookie names, LocaleMeta/LocaleStatus   (no React, no next/*)
  types.ts           Dictionary, MessageKey, TFunction, DeepPartial          (types only)
  translate.ts       lookup / interpolate / translate / createT / flattenCatalog
  resolve.ts         parseAcceptLanguage / matchLocaleTag / resolveLocale    (pure, unit tested)
  server.ts          getLocale() / getT()                                    (RSC, route handlers, actions)
  index.tsx          'use client' — I18nProvider / useI18n / useT            (client tree)
  locales/zh-CN.ts   the catalog; `Dictionary = typeof zhCN`
  locales/en.ts      `satisfies Dictionary` → a missing key is a compile error
  locales/ja|ko|es.ts `satisfies DeepPartial<Dictionary>` → status: 'partial'
  locales/index.ts   DICTIONARIES map (fr/de/ru/ar alias `en`)
```

| Surface | Signature | Use in |
| --- | --- | --- |
| `getLocale()` | `Promise<LocaleCode>` | RSC / route handlers |
| `getT()` | `Promise<TFunction>` | RSC |
| `useT()` | `TFunction` | client components |
| `useI18n()` | `{ locale, setLocale, t, locales, isPartial }` | client components (locale-only consumers unchanged) |
| `t(key, vars?)` | `(MessageKey, Record<string, string \| number>) => string` | everywhere |
| `translate(locale, key, vars?)` | runtime / untyped key | tests, tooling, dynamic keys |
| `resolveLocale({ cookie, acceptLanguage })` | `LocaleCode` | request plumbing, tests |

**Resolution order:** cookie `locale` → legacy cookie `NEXT_LOCALE` → `Accept-Language` (q-ordered) → `zh-CN`.
`zh-TW`, `zh-Hant-HK`, … all map to `zh-CN`. Malformed headers degrade to `zh-CN`, they never throw.

**Per-key fallback:** requested locale → `en` → `zh-CN` → the key string itself. `undefined` is never renderable.
`ja/ko/es` are marked `status: 'partial'` in `config.ts` (in code, not in the UI — switching to Japanese is not
visibly different from before); `fr/de/ru/ar` are `status: 'fallback-en'`.

**Persistence** is cookie-based (`locale`, plus legacy `NEXT_LOCALE`), so SSR and the first client render agree.
`localStorage` is written as a compatibility copy for `global-translator.tsx`, never as the source of truth.

## 2. Key convention

* Dotted, namespaced, `<area>.<subarea>.<leaf>`: `nav.home`, `article.readMore`, `home.hero.ctaRead`.
* Areas in use: `layout` (root metadata), `nav`, `footer`, `home` (+ `home.hero`, `home.error`, `home.wallet`,
  `home.uniswap`, `home.ontology`), `article`, `login`, `modules`, `moduleDescs`, `stats`, `common`, `founder`, `app`.
* Leaves are **strings only** — no arrays, no markup. Emoji, `→`, `▲` and leading/trailing spaces that are part of
  the visible text stay inside the value so `zh-CN` output is byte-identical to the pre-i18n markup.
* Interpolation is `{name}`: `t('article.royalty', { rate: '5.0', license: 'CC-BY' })`.
  Unknown placeholders are preserved verbatim, never replaced with `undefined`.
* Values are sentence-case copy, never keys-as-copy: `zh-CN` must read like the current product.
* Reuse before adding: `common.retry`, `nav.write`, `modules.tech` are shared across components.

## 3. Adding a locale

1. `src/lib/i18n/config.ts` — append the code to `LOCALE_CODES`, add a `LOCALES` entry
   (`{ code, label, nativeLabel, flag, ogLocale, status }`), and a `LANGUAGE_SUBTAG_TO_LOCALE` entry.
2. `src/lib/i18n/locales/xx.ts` — `const xx = { … } satisfies DeepPartial<Dictionary>` (or `satisfies Dictionary`
   for a complete translation) and `export default xx`.
3. `src/lib/i18n/locales/index.ts` — import it and add it to `DICTIONARIES`.
4. Nothing else: the switcher, the resolver, `getT()` and `createT()` all read the registry.
5. `npx vitest run` — `resolves every key in every locale without rendering undefined` covers the new locale
   automatically, and the completeness test still enforces `zh-CN ⊆ en`.

Missing keys are allowed only under `DeepPartial`; they fall back per key to `en`, so a half-finished locale
fails loudly where it matters (a key wrongly typed or misspelled) and degrades gracefully where it does not.

## 4. Migration recipe (one component, ~10 lines)

```tsx
// 1. add the zh string to locales/zh-CN.ts under the right namespace
// 2. add the en string to locales/en.ts (compiler enforces it)
// 3. client component:  const t = useT();            RSC: const t = await getT();
// 4. replace a literal:      <span>发布</span>              → <span>{t('common.publish')}</span>
// 5. replace a ternary:      isEn ? 'Write' : '写作'        → {t('nav.write')}
//    (zh value must be exactly the old literal — no copy edits in this step)
// 6. replace literals maps:  { tech: '科技前沿', … }        → { tech: 'modules.tech', … } + t(key)
// 7. interpolate:            '版税: ' + x + '%'             → t('article.royalty', { rate: x })
// 8. delete the now-dead `isEn` local and unused props
// 9. npx tsc --noEmit   (unknown/typo'd keys fail here)   npx vitest run
// 10. re-run the counter below and update the row in §6
```

Rules that keep the slice honest:

* Never change a `zh-CN` value while migrating — move the byte string, do not rewrite it.
* `isEn ?` on a *value* is a smell: only one branch is real product copy; the other is a translation.
* Comments stay Chinese; they are not user-visible. `docs/I18N.md` counts non-comment CJK only.
* A component is "done" when `grep -n '[\x{4e00}-\x{9fff}]' file` only matches comments.

`tests/i18n.test.ts` locks down: every `zh-CN` key exists in `en` (and `en` adds no extras); unknown keys fall back

`Accept-Language` absent → `zh-CN`, `en-US` → `en`, `zh-TW` → `zh-CN`, malformed → `zh-CN`, q-ordering and `q=0`
exclusion; cookie beats header; `{name}` interpolation and unknown-placeholder preservation.

## 8. Known limitations / risks

1. **The root layout reads cookies** (`getLocale()` in `RootLayout` + `generateMetadata`). That is what makes SSR
   match the `locale` cookie and keeps `<html lang>` and OG `locale` correct, but it also opts every route out of
   static/ISR caching. `/p/[id]` previously benefited from `revalidate = 300`. Mitigation if that hurts: keep the
   layout static and move locale-aware chrome into client components, or enable PPR/cacheComponents with the
   provider wrapped in `<Suspense>`. This is the single biggest risk in this change.
2. **`global-translator.tsx` is still mounted.** It walks the DOM for non-`zh-CN` locales and rewrites Chinese text
   node-by-node with a 190-line hardcoded map. For migrated surfaces it is a no-op (the text is already English),
   but it is the reason the unmigrated 22 UI components still "work" in English. Delete it only after the last of
   those is migrated — until then it is load-bearing, and any string it does not know stays Chinese for `en` users.
3. **Catalog drift.** `zh-CN` is the source of truth and `en` is compiler-enforced, but `ja/ko/es` are
   `DeepPartial` on purpose. Silent English in a Japanese UI is expected until those files are finished.
4. **Dynamic strings are outside the type system.** Article titles, author names, DIDs, API `error` messages and
   AI output are data; `t()` never sees them. Agent-facing API errors (76 lines in `app/api/**`, 95 in
   `lib/web5/api/errors.ts`) are still Chinese-only and need a product decision before they are translated.
